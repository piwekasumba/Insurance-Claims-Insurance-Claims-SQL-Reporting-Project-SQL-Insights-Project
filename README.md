# Insurance Claims Risk Analytics — SQL Insights Project
---
## Project Overview

This is a self-directed PostgreSQL SQL portfolio project using simulated insurance claims data.

The project explores how SQL can organise claims, customer and policy information into structured reporting outputs. It focuses on claims measures, category comparisons, settlement analysis, data-quality checks and operational monitoring.

The purpose is to practise the SQL and reporting logic used to investigate business questions and communicate patterns in structured data.

All data is simulated and does not represent real policyholders, insurance claims or an actual insurance company.
---
## Reporting Questions

The analysis explores questions such as:

- How many claims are recorded in the sample?
- How are claims distributed across categories and statuses?
- How do recorded claim amounts differ across groups?
- What patterns appear across customers and policies?
- How are settlement measures represented?
- What exceptions or missing values should be investigated?
- Do reporting outputs reconcile with the underlying data?
---
## SQL Techniques

The project provides practice with PostgreSQL and SQL techniques including:

- Relational joins
- Filtering and aggregation
- GROUP BY and aggregate functions
- CASE expressions
- Common Table Expressions
- Window functions
- Reporting views and summary outputs
- Data-quality and exception checks
- Row-count and amount reconciliation
---
## Data Quality and Reporting Controls

Data-quality checks are important because missing, inconsistent or unmatched records can affect reporting results.

The project includes checks intended to investigate missing values, unmatched records, duplicate identifiers, invalid values and differences between source and reporting outputs.

These checks are designed to identify records for review. An exception does not automatically establish fraud, incorrect behaviour or a confirmed business risk.
---
## Interpreting Claims Indicators

Claims categories, claim amounts, frequency and severity groupings can provide descriptive reporting indicators.

They should not be treated as predictive risk scores, confirmed fraud findings or evidence of causation.

Any rate or percentage must be interpreted using its stated numerator, denominator, population and reporting period.

## Project Context and Limitations

This is independent learning and portfolio work using simulated data.

It does not represent professional insurance experience, a production claims system, actuarial modelling, fraud detection software or a predictive risk model.

The project demonstrates SQL reporting practice and careful interpretation of descriptive claims information.
